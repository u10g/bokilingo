# 簿記3級学習アプリ 設計ドキュメント

Sep 27, 2026 · @u10

## プロダクト概要

Duolingo型の学習体験を日商簿記3級に適用したReact製モックアップ。単一ファイル約2,400行、4コース・全230問を実装済み。

当初の検証目的は3点あり、いずれも結論が出た。

| 検証したかったこと | 結論 |
| --- | --- |
| Duolingo風の蛇行パスUIは簡単に作れるか | 作れる。SVGを使わず縦1カラム＋`translateX`で十分な再現度 |
| 1セット10問の形式は簿記に合うか | 部分的に合う。暗記・分類系は合うが、仕訳は5〜8問が適切 |
| 問題形式は何種類必要か | 5形式。特に仕訳は金額入力より単語バンク方式が有効だった |

最大の発見は、当初計画になかった仕訳穴埋め形式（単語バンク方式）が最も簿記に適していた点。金額入力を廃し勘定科目の判断だけに絞ることで、Duolingoのテンポ感と簿記の思考を両立できた。

## 要件定義

2026年11月の日商簿記3級合格に向け、通勤時間などの細切れ時間で勘定科目と仕訳を反復するための個人用アプリ。出題区分表は「簿記検定試験出題区分表 2022年度適用」に準拠する。

### ユーザーストーリー

- 学習者として、アプリを開いてすぐ次にやるレッスンが分かるようにしたい
- 学習者として、勘定科目がどの要素かを瞬時に判断できるようになりたい
- 学習者として、仕訳で「どちら側に何を置くか」を体で覚えたい
- 学習者として、間違えた問題だけを後から復習したい
- 学習者として、教科書の進度に合わせて学ぶ順番を選びたい

### 非機能要件

- スマートフォン縦画面（幅375px前後）で破綻しない
- 出題順は毎回シャッフルし、並び順の丸暗記を防ぐ
- 保存に失敗してもアプリの利用は継続できる
- 課金要素を持たないため、ライフ切れで学習が止まらない

### スコープ外

音声・スピーキング問題、リーグやフレンドなどの対人要素、複数端末間の同期、サーバーサイドの実装、課金とライフの時間回復。

## システム構成図

&#91;embedded content: アプリ構成 · 4層、単一ファイル\]

状態はすべてルートの `BokiApp` が持ち、画面コンポーネントはpropsで受け取って表示するだけの構造にしている。サーバーもビルド工程もなく、単一ファイルで完結する。

## 技術スタック

ビルド工程もサーバーも持たない構成を選んだ。個人の学習用途で、反復して手を入れる前提のため。

| 領域 | 採用 | 理由 |
| --- | --- | --- |
| UI | React（単一ファイル・関数コンポーネント） | 画面数が少なく、状態をルートに集約できる |
| 状態管理 | `useState` のみ | 状態が10個程度で、外部ライブラリを入れる必要がない |
| スタイル | Tailwind CSS（コアユーティリティのみ） | 設定ファイル不要でDuolingo風の立体ボタンを再現できる |
| アイコン | lucide-react | Flame・Heart・Gem・Trophy など必要な記号が揃う |
| 永続化 | `window.storage` | 単一キーにJSONで保存。端末内に閉じる |
| 図形描画 | なし（CSSのみ） | 蛇行パスは `translateX` で足りるため、SVGライブラリは不要 |

### 制約と、それに対する設計

- 単一ファイルのためコード分割ができない。問題データを先頭に集約し、コンポーネント定義と明確に分離して可読性を保っている。
- `localStorage` ではなく `window.storage` を使う。非同期APIのため、初回読み込み中は「よみこみ中…」を表示する。
- 外部フォントを読み込めないため、Duolingo独自の丸ゴシックは再現せず `font-extrabold` とシステムフォントで近似している。
- 保存・読み込みはすべて `try-catch` で囲み、失敗してもメモリ上での動作を継続する。

## データ設計

コース → 章 → レッスン → 問題の4階層。レッスンはフラットな配列で持ち、`chapter` の値が変わった箇所で章バナーを差し込む。この持ち方により、解放判定を配列のindexと `completedSet` の比較だけで済ませている。

### コース

```javascript
{
  id: "accounts",              // 永続化のキーにもなる
  title: "勘定科目コース",
  subtitle: "選択式で勘定科目を一気に覚える",
  chapters: ACCOUNTS_CHAPTERS,  // 章IDから見出し・配色への対応表
  nodes: ACCOUNTS_NODES,        // レッスンのフラット配列
  stubNote: "…準備中"           // 末尾のプレースホルダ文言
}
```

### レッスン

```javascript
{
  id: "ac-a1",
  title: "商品を仕入れて売る",
  kind: "concept",    // concept | training | checkpoint
  chapter: "scA",
  desc: "三分法で商品売買を記録するときの科目です。",
  questions: [ /* 問題オブジェクト */ ]
}
```

`kind` はマップ上のアイコンと進行ルールを決める。`concept` は本アイコン、`training` はダンベル、`checkpoint` はトロフィーで表示し、`checkpoint` だけ合格判定が働く。

### 収録コース

| コース | 章 | レッスン | 問題 | 主な形式 |
| --- | --- | --- | --- | --- |
| 勘定科目コース（標準） | 10 | 31 | 253 | 5要素分類 |
| 仕訳穴埋めコース | 7 | 21 | 116 | 仕訳穴埋め |
| TAC出版準拠コース | 2 | 11 | 62 | 分類・二択・仕訳 |
| 思考パターン別コース | 3 | 5 | 26 | 二択・仕訳 |

勘定科目コースと仕訳穴埋めコースは、同じ「使う場面」で章立てを揃えている。同じ場面を科目の分類と仕訳の両面から学べるようにするため。

### 場面別の章立て

| 章 | 場面 |
| --- | --- |
| A | 商品を仕入れて売る |
| B | お金を持つ・預ける |
| C | 貸し借りと手形 |
| D | 従業員とお金 |
| E | 会社を運営する経費 |
| F | 固定資産を持つ |
| G | 決算で整理する |
| H | 税金を納める（勘定科目コースのみ） |
| I | 会社の元手と利益（勘定科目コースのみ） |

答えの種類ではなく場面で章を切ったのが設計の要点。当初は資産・負債・費用…と答え別に章を作ったが、章内の全問が同じ答えになり分類の練習にならなかった。場面別に組み直した結果、全レッスンで答えが2種類以上に分散している。

同じ科目が複数のレッスンに繰り返し登場するのは意図的で、現金や売掛金のような頻出科目は場面を変えて何度も問われる。

## 問題形式設計

`QuestionRenderer` が `format` で分岐し、採点・入力完了判定・正解文言・初期値の4つのヘルパーが同じ分岐を持つ。形式を追加するときはこの5箇所を揃える。

| format | 画面 | 入力 | 採点 |
| --- | --- | --- | --- |
| `classify` | 科目名を大きく表示 | 5要素ボタンから1つ選ぶ | 完全一致 |
| `twochoice` | 設問文を表示 | 2択ボタン | 完全一致 |
| `fillblank` | 空欄入りの文 | 語群から1つ選ぶ | 完全一致 |
| `journal` | 取引文 | 科目プルダウン＋金額入力 | 借貸の科目と金額すべて一致 |
| `journalBlank` | 取引文＋仕訳表 | 単語バンクから空欄へ | 全空欄の科目が一致 |

### 仕訳穴埋め（journalBlank）

本コースの中核となる形式。Duolingoの単語バンク方式を仕訳表に適用した。

```javascript
{
  id: "jb1-q7",
  format: "journalBlank",
  blankSide: "credit",        // 空欄にする側。片側だけを問う
  prompt: "商品60,000円を仕入れ、20,000円は現金で支払い、残額は掛けとした。",
  rows: [
    { debitAnswer: "仕入", debitAmount: 60000,
      creditAnswer: "現金", creditAmount: 20000 },
    { debitAnswer: null,  debitAmount: 0,
      creditAnswer: "買掛金", creditAmount: 40000 }
  ],
  choices: ["現金", "買掛金", "売掛金", "売上"],
  explanation: "貸方が2行に分かれます。…"
}
```

設計上の要点は4つある。

1. **片側だけを問う**。`blankSide` で空欄側を指定し、反対側は答えを最初から見せる。両側を空欄にすると埋める順番に迷い、かえって混乱したため。空欄側の列見出しを青くして、どちらを答えるかを明示する。
2. **金額は最初から埋める**。勘定科目の判断だけに集中させる。金額入力を伴う `journal` 形式と役割を分けている。
3. **選択肢からヒント側の科目を除く**。表示済みの科目が選択肢に並ぶと紛らわしいため、全問で混入がないことを検証している。
4. **複合仕訳に対応**。`rows` を配列にし、片側だけ行数が多い仕訳を表現できる。`debitAnswer: null` で空セルを表す。現状は最大3行・空欄3つまで出題している。

### トークン方式

選択肢は `{ id, label }` のトークンとして扱う。`id` は `${問題id}::c${選択肢index}` で、同じ科目名が選択肢に複数あっても区別できる。

- バンクの語をタップすると、選択中の空欄（未選択なら先頭の空き）に入る
- 埋まったセルをタップすると語がバンクに戻る
- 空欄が2つ以上あるときは、セルをタップして入れ先を選べる
- 取り出した語の位置には同じ大きさの灰色プレースホルダが残り、レイアウトが動かない

### マップのUI

蛇行パスはSVGを使わず、縦1カラムの各ノードに `translateX` を与えて実現している。オフセット値は8段階の配列を循環させる。

ノードは3状態を色とアイコンで区別する。

- **クリア済み**：金色・星
- **現在地**：緑・パルスリングと「スタート」の吹き出し
- **ロック**：灰色・南京錠

レッスンが31個あるため、マップを開いたときに現在地まで自動スクロールする。

## ゲーム進行ルール設計

### ライフ

Duolingoと異なり、ライフは**当日の誤答数から導出する値**として定義した。

```javascript
const hearts = Math.max(0, 5 - wrongToday.length);
```

課金も時間回復も持たないため、回復手段を学習行為そのものに結びつけている。復習画面で誤答した問題を正解すると、その問題がリストから外れてライフが1つ戻る。全問正解すればフル回復する。日付が変わると誤答リストは自動的に空になる。

この設計により、ライフ切れが「課金への誘導」ではなく「復習への誘導」になる。

### 誤答時の挙動

1. 即座に赤いフィードバックバーで不正解を示し、正解と解説を表示する
2. その問題をセッション末尾のキューに戻す
3. 当日の誤答リストに追加する（同じ問題は重複登録しない）

レッスンは全問正解するまで終わらない。誤答すると残り問題数が増えるため、ヘッダーに「のこり◯問／全◯問」を表示している。

### チェックポイント

章末のチェックポイントだけ合格判定が働く。

| 判定 | 条件 | 結果 |
| --- | --- | --- |
| 合格 | 正答率70%以上 | クリア扱い。次のレッスンが解放される |
| 不合格 | 正答率70%未満 | 未クリア。「もう一度挑戦する」を表示 |

正答率は誤答した**問題の種類数**で判定する。再出題で最終的に全問正解しても、一度でも間違えた問題は不正解として数える。

### スキップ

Duolingoと異なり、ロック中のレッスンも「スキップしてレッスンを始める」から着手できる。教科書の進度に合わせて任意の単元から始めたい場合に対応するため。

進行管理は「解放済みindex」ではなく `completedSet` と「最初の未完了ノード」で行っているので、スキップして先に進んだ後から前のレッスンを個別にクリアできる。

### その他の記録

- **ストリーク**：レッスンクリアまたは復習正解の時点で更新。前回が昨日なら+1、2日以上空いていれば1にリセット。同日中の2回目以降は変化しない
- **XP**：レッスンは問題数×10、復習の正解は5
- **クリア問題数**：同じレッスンを再挑戦するたびに加算される累計値

### 出題順

挑戦ごとに `attemptId` を更新し、それをReactの `key` に渡してレッスン画面を作り直す。これにより毎回シャッフルされ、並び順で正解を覚えてしまうのを防ぐ。

## 永続化設計

単一キー `boki-quest-progress-v1` に全進捗をJSONでまとめて保存する。個人データとして端末内に閉じ、他の利用者には見えない。

### 保存スキーマ

```javascript
{
  activeCourseId: "accounts",
  completedSets: {              // Set は配列に変換して保存
    accounts:     [0, 1, 2],
    journalBlank: [],
    tac:          [],
    pattern:      []
  },
  solvedCount:   253,           // 累計クリア問題数
  totalXp:       2530,
  streak:        4,
  lastActiveDate: "2026-09-27", // ストリーク判定の基準日
  wrongToday:     [ /* { key, nodeTitle, question } */ ],
  wrongTodayDate: "2026-09-27"  // 日付が変われば誤答リストを破棄
}
```

### 保存タイミング

毎問ではなく、進捗が確定する4つの契機でのみ保存する。保存回数を抑えるため。

- 問題を間違えたとき
- 復習で正解したとき
- レッスンをクリアしたとき
- コースを切り替えたとき

### 日付の扱い

端末のローカル日付を `YYYY-MM-DD` の文字列で持ち、日数差で判定する。

| 場面 | 処理 |
| --- | --- |
| 誤答リストの日付が今日でない | リストを破棄してライフをフル回復 |
| 最終学習日から2日以上空いた | ストリークを0にリセット |
| 最終学習日が昨日 | ストリークを+1 |
| 最終学習日が今日 | ストリークは変化しない |

### 堅牢性

- 読み書きはすべて `try-catch` で囲み、失敗してもアプリは動作を継続する
- 初回起動時など保存データがない場合は既定値で開始する
- 保存済みの `activeCourseId` が現在のコース一覧に存在しない場合、標準コースにフォールバックする。コース構成を変更しても保存データで壊れないようにするため
- 読み込み完了までは「よみこみ中…」を表示し、未確定の状態を見せない

### データ削除

「学習の記録」画面の末尾に削除導線を置いている。誤操作を防ぐため2段階の確認を挟む。

## 設計上の判断と今後の拡張

### 主要な意思決定の記録

反復のなかで方針を変えた判断を、理由とともに残す。

| 判断 | 当初案 | 変更後 | 理由 |
| --- | --- | --- | --- |
| 章の切り方 | 答えの種類別（資産・負債…） | 使う場面別 | 章内の全問が同じ答えになり、分類の練習にならなかった |
| 仕訳の入力 | 科目プルダウン＋金額入力 | 単語バンクで科目のみ | 金額入力が思考を分散させた。科目判断に集中させる |
| 仕訳の空欄 | 借方・貸方の両側 | 片側のみ | 両側だと埋める順番に迷い混乱した |
| ライフ | 5個から減る独立した値 | 当日の誤答数から導出 | 課金がないため、回復を復習に結びつけた |
| 1セットの問題数 | 一律10問 | ノード種別ごとに可変 | 仕訳は1問の負荷が高く、10問続くとだれる |
| 進行管理 | 解放済みindex | `completedSet` | スキップ後に前のレッスンへ戻れるようにするため |

### 検証済みの項目

仕訳穴埋めコースの全116問について、機械的に検証している。

- 借方合計と貸方合計が一致する
- 正解の科目が選択肢に含まれる
- ヒント側に表示される科目が選択肢に混入していない
- 選択肢に重複がない
- 正解時に正解、1箇所誤りで不正解、未入力で未完了と判定される
- 問題IDに重複がない

勘定科目コースについては、指定した90科目を過不足なくカバーし、同一科目の分類が全レッスンで一貫していることを確認済み。
